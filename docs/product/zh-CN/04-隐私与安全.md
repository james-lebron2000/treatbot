# 隐私与安全（PHI/合规）

> 目标：在 Demo 阶段也要具备“默认保护”的产品姿态，避免把敏感医疗信息在无意识下外发或长时间留存。

## 1. 数据分类与最小化

- **高敏（PHI/PII）**：姓名、电话、身份证号、住院号、完整病历全文、影像报告全文等
- **业务必要**：诊断、分期、关键基因、治疗史、体能评分等（尽量结构化后使用）

建议：
- 上传原始文件仅用于 OCR/解析；后续尽量使用结构化字段进行匹配
- 前端展示时区分“可编辑字段”和“原文”，避免误复制传播

## 2. LLM 外发控制（建议默认关闭或强脱敏）

环境变量：`LLM_PHI_MODE`
- `full`：允许 LLM；仅在明确知情同意与脱敏策略完善后使用
- `redact`：更激进脱敏；可能降低匹配质量
- `disallow`：禁止任何会将医疗文本外发给第三方模型的调用（推荐默认）

注意：
- 如果你启用了 `STRICT_MODE=true` 或 `REQUIRE_LLM=true`，则必须使用 `LLM_PHI_MODE=full` 或 `redact`；`disallow` 会直接阻止所有 LLM 相关能力。

> 运营侧建议：在产品 UI 上提示当前模式，避免“以为在本地处理但实际外发”的误解。

## 3. 访问控制

- 所有业务接口默认需要 JWT（`Authorization: Bearer <token>`）
- Token 过期后应触发重新登录
- 建议后续加入：
  - 账号风控（IP/设备指纹）
  - 更细粒度 RBAC（运营/医生/管理员）

## 4. 日志与留存

建议原则：
- 日志中默认不打印病历全文、OCR 原文、密钥与 token
- 为每次请求保留 `traceId`（便于定位，但不包含敏感内容）
- 匹配历史留存设置上限（例如 `MATCH_HISTORY_MAX`）

## 5. 上传文件的存储策略（建议）

- Demo：本地/容器挂载 `./uploads`（便于演示）
- 生产：
  - 加密存储（KMS）
  - 设定生命周期（自动删除）
  - 权限隔离（按租户/用户）

## 6. 安全基线（上线前最小要求）

- `JWT_SECRET` 使用高强度随机值
- 不在前端 bundle 中暴露任何密钥（仅使用 `NEXT_PUBLIC_*` 的非敏感配置）
- 禁止将 `.env`、OCR 密钥等提交到公共仓库
- 对上传接口加大小/类型限制（避免 DoS 与恶意文件）
