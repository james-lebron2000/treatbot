# 目标架构与演进（CTO/CMO 联合审视）

> 目标：在 **Mac mini 单机**条件下支撑 **10000 病人、3 年留存、峰值 100 用户**，并具备“可审计、可备份、可迁移到云端”的演进路径。

## 1. 关键非功能指标（必须明确）

### 容量
- 病历原文件：10000 × 20MB ≈ **200GB**（不含备份冗余）
- 数据库（结构化字段、OCR 文本、匹配结果、索引）：通常 **10–50GB** 量级
- 备份：建议至少 **2×**（本地快照 + 异地拷贝），因此磁盘规划建议 **≥ 1TB SSD**

### 并发
- 峰值在线 100：主要压力来自上传与 OCR/解析，必须：
  - 限制单文件大小、并发数与速率（rate limit）
  - 异步化耗时任务（队列/worker）
  - 前端用 SSE 分批返回结果，避免长请求超时

### 合规与安全（医学场景底线）
- PHI 默认不外发：`LLM_PHI_MODE=disallow`
- 上传文件加密存储（Mac：FileVault；外接盘：APFS 加密）
- 有清晰的数据留存与删除策略（3 年留存 → 到期可删除且可审计）
- 访问与操作可追踪（最少：请求 traceId + 关键操作日志；理想：审计事件表）

## 2. Mac mini 单机“目标运行形态”（Phase 0/1）

### 2.1 组件分层

**访问层**
- 浏览器（运营/医生助理/患者）
- 反向代理（建议：Caddy/Nginx，负责 HTTPS、限流、静态压缩、WAF 基础规则）

**应用层**
- Next.js 前端（含 `/api/*` 代理）
- Node.js/Express 后端（API + 业务）
- Worker（匹配/解析等耗时任务；可与后端同进程或独立进程）

**数据层**
- MongoDB（当前实现）：用户/患者/病历结构化/任务状态/匹配结果
- Redis（可选但推荐）：队列、任务状态、节流缓存

**存储层**
- 本地文件系统（bind mount）：原始病历文件（20MB）与 uploads

**观测与运维**
- `/api/health`（健康）
- `/api/metrics`（指标）
- 结构化日志（JSON + traceId）
- 备份脚本（数据库 dump + 文件增量备份）

### 2.2 单机目录规划（强约束）

建议把所有持久化数据集中在 `HOST_DATA_DIR`（外接 SSD 更佳）：
- `${HOST_DATA_DIR}/mongodb`：MongoDB 数据
- `${HOST_DATA_DIR}/redis`：Redis 数据（可丢）
- `${HOST_DATA_DIR}/uploads`：病历原始文件（主要容量）
- `${HOST_DATA_DIR}/backups`：备份文件（建议定期清理）

> 这样做的收益：迁移到云端/新机器时，只需要搬走一个目录即可恢复大部分状态。

### 2.3 单机性能建议（经验值）

- CPU：Apple Silicon 8 核及以上
- 内存：**16GB 起步，推荐 32GB**（OCR/解析、并发上传、Node 内存更稳）
- 磁盘：**≥ 1TB SSD**（200GB 数据 + 备份冗余 + 系统与缓存）
- 网络：上行带宽越大越好；外网访问必须上 HTTPS 与基础防护

## 3. 数据流（从上传到匹配）

1) 上传文件 → 保存到 `uploads`（本地文件系统）并生成文件元数据（checksum、mime、大小、归属 patientId）  
2) OCR → 得到文本（可保存为版本）  
3) 解析 → 结构化字段（诊断、分期、突变、治疗史…）  
4) 匹配 → 生成候选试验 + 解释 + 缺失项提示  
5) 只保存最近 1 次匹配（`MATCH_HISTORY_MAX=1`），避免历史膨胀  

## 4. 当前方案的关键缺口（必须补齐）

### 4.1 留存策略未自动化
需求：3 年留存 → 到期后可删除（dry-run + 审计 + 真删开关）。  
风险：长期运行会堆积、且无法回答“哪些数据按策略删除了？”

### 4.2 备份与恢复链路不闭环
必须具备：
- 数据库可导出/可恢复（定期 dump）
- 上传文件可增量备份（rsync/Time Machine/对象存储）
- 定期演练恢复（否则备份等于没有）

### 4.3 医学安全治理缺失
必须明确：
- 输出是“候选试验筛选与解释”，不是诊断/处方
- 对缺失关键字段要强提示，避免误判
- 有版本管理：匹配规则、试验数据、模型提示词的变更可追溯

## 5. 演进路线（从单机到云端，保持最小改动）

### Phase 2：托管数据库 + 对象存储（最常见演进）
- 数据库：迁移到托管 Postgres 或托管 Mongo（择一）
- 文件：迁移到对象存储（S3/OSS），数据库只存 key/url + hash
- 应用仍可在 Mac mini 或云主机跑

### Phase 3：全云/多租户/高可用
- 多实例后端（水平扩展）
- 队列与 worker 独立扩容
- 细粒度 RBAC + 全量审计（谁访问了谁的数据）
